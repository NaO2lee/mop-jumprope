# 40-카메라 스케일 — 아키텍처 옵션 분석

**작성일**: 2026-05-13
**대상**: 김PD `today119/mop-jumprope`, 현재 NaO2lee fork dev 브랜치에서 안정화 중
**전제**: 최대 40 코트 동시 운영, 각 카메라당 시청자 추정 약 30명 (심판 1 + 운영 2 + 관객·관계자 ~25)

---

## 0. 현재 아키텍처 (PeerJS WebRTC mesh)

```
[카메라 폰 1] ─┬─→ [심판 1]
              ├─→ [운영자]
              ├─→ [관객 1]
              └─→ [관객 N]    (peer-to-peer 직접 연결)

[카메라 폰 2] → ...
```

**문제점**:
- 각 카메라가 모든 viewer 에게 **개별 stream** 송출 → 업로드 대역폭 = N × bitrate
- 30 viewer × 1Mbps = **30 Mbps upload** per camera 필요
- 일반 가정/모바일 회선 업로드는 5-20 Mbps → **5-10명 넘으면 끊김**
- 40대 동시 안정 운영 불가

---

## 옵션 A · SFU 자가 호스팅 (LiveKit OSS / Mediasoup / Janus)

**구조**: 카메라 → SFU 서버 → 모든 viewer 에게 fan-out.

```
[카메라 N] ──(1Mbps 1개 스트림)──→ [SFU 서버] ──(30개 fan-out)──→ [viewer N]
```

**스펙**:
- 카메라 업로드: 1 Mbps (viewer 수와 무관)
- 서버 outbound: 40 카메라 × 30 viewer × 1 Mbps = **1.2 Gbps peak**
- 서버 사양: 16 vCPU + 32GB RAM + 10Gbps NIC (Hetzner CX42 등 = 월 ~$50)
- 지연: **100-300ms** (가장 낮음)

**비용** (3일 행사 기준):
- VPS: 월 $30-80 (사용 안 할 때도 부담)
- 트래픽: 1.2 Gbps × 8시간 × 3일 = ~13 TB. Hetzner 무제한 OK, AWS 라면 추가 비용
- **세팅 시간**: 2-3일 (Docker compose 로 LiveKit 띄우고 클라이언트 SDK 통합)

**장점**:
- 가장 낮은 지연
- 카메라 폰 업로드 부담 ↓
- 자가 호스팅이라 데이터 외부 유출 X

**단점**:
- 서버 운영 책임 (모니터링·재시작·SSL)
- 첫 셋업 학습 곡선
- 행사 당일 서버 장애 = 전체 마비 위험

## 옵션 B · YouTube Live RTMP

**구조**: 각 카메라가 YouTube Live 채널로 RTMP 스트림 송출. 시청자는 YouTube 임베드로 시청.

```
[카메라 N (OBS)] ──(RTMP)──→ [YouTube Live] ──(HLS embed)──→ [모든 viewer]
```

**스펙**:
- 카메라 업로드: 1-3 Mbps (RTMP 인코딩)
- 서버: **YouTube 가 처리** → 우리 부담 0
- 지연: **3-10 초** (저지연 모드 사용 시 2-5초)
- 시청자 수 제한: **무한대**

**비용**:
- **완전 무료** (YouTube 가 모든 트래픽 부담)
- 카메라 송출 장비: 폰만 있으면 OK (Streamlabs/Larix Broadcaster 앱)

**단점**:
- **지연 3-10초** → 심판이 실시간 검토 불가 (탭 카운트는 지연 영향 없으니 OK, 다만 비디오 확인은 늦음)
- 40개 YouTube 채널 동시 운영 = YouTube 정책상 1 계정으로 가능하나 각각 사전 생성 필요
- 영상 검토/녹화는 YouTube VOD 로 다운로드 (자동 1080p MP4)

**적합도**:
- **관객 시청 채널로 최적** (지연·비용·확장성 모두 합격)
- 심판 실시간 검토용으로는 부적합

## 옵션 C · PeerJS 유지 + viewer 제한

**구조**: 카메라당 viewer 1-2명만 직접 연결. 나머지 viewer 는 다른 경로(YouTube/녹화 후 검토).

```
[카메라 N] ──(WebRTC 1:1)──→ [심판 1명만]
              (다른 viewer 는 YouTube 또는 검토용 영상)
```

**스펙**:
- 카메라 업로드: 1-2 Mbps (1-2 viewer)
- 서버: PeerJS 시그널링만 (현재 무료 PeerJS Cloud 또는 자가 호스팅)
- 지연: **<100ms** (WebRTC 직결)

**비용**:
- 거의 무료 (PeerJS 시그널링 서버만 필요)

**단점**:
- viewer 분리 운영 (심판은 PeerJS, 관객은 YouTube)
- 두 시스템 동기화 책임 → 코드 복잡도 ↑

**장점**:
- 기존 코드 변경 최소
- 심판은 즉시 영상 확인 (지연 없음)

## 옵션 D · 하이브리드 (추천)

**구조**: 옵션 B + C 결합. 각 역할에 맞는 채널 사용.

```
                      ┌─→ [YouTube Live] ──→ [관객 N명]
[카메라 폰] (OBS) ─────┤
                      ├─→ [PeerJS WebRTC] ──→ [심판 (저지연 검토)]
                      └─→ [로컬 녹화] ──→ [NAS (사후 검토·증거)]
```

**스펙**:
- 카메라당 업로드: 3-5 Mbps (RTMP 1Mbps + WebRTC 1Mbps + 로컬 녹화 0Mbps)
- 서버 비용: PeerJS 시그널링만 (~$0)
- YouTube 트래픽: 무료 (관객 시청)
- 지연:
  - 심판: <100ms (WebRTC)
  - 관객: 3-10s (YouTube)
- 녹화: NAS 영구 보관

**비용 계산** (3일 행사):
- 인프라: $0 (YouTube + PeerJS Cloud + NAS 일회성 ~140만원)
- 카메라 송출 장비: 폰 + OBS 무료
- 운영 인력: 행사 전 1회 셋업

**셋업 작업** (40대 기준):
1. 각 카메라 폰에 OBS 또는 Streamlabs 앱 설치, YouTube 스트림 키 입력
2. PeerJS 코드는 그대로 (심판 1:1 연결 유지)
3. NAS WebDAV 마운트, OBS 가 로컬 녹화 자동 sync

**장점**:
- 비용 거의 0
- 각 채널이 자기 역할 최적
- 한 채널 장애 시 다른 채널로 폴백 가능 (redundancy)

**단점**:
- 카메라 송출 장비 셋업 다소 복잡 (OBS 설정)
- 40대 OBS 동시 관리 → 매뉴얼·체크리스트 필요

## 추천 — 옵션 D (하이브리드)

1. **비용 0** (NAS 는 어차피 task #103 녹화 저장용으로 필요)
